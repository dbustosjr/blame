# Run the F24 reviewer as a GitHub Action in the user's repo with the user's key; local `blame review` as a second entry point; hosted worker later

## Context and Problem Statement

Week 0 decision W0-3: where does the independent reviewer run? It must review every PR in a connected repo, including PRs from Cursor and Claude Code, within 5 minutes p90 (R-PERF-3), with a codebase index and past bugs, at $0 to David, without Blame holding provider keys by default (R-BYOK-4).

## Decision Drivers

* $0 to David at pilot scale; InsForge Free custom compute is 120 h a month, not enough for an always-on worker ([pricing](https://insforge.dev/pricing))
* No provider key custody by default (R-BYOK-4)
* Source code stays out of Blame servers (R-RET-2)
* Fires on every PR, whoever wrote it (DEC-6)
* Untrusted PR content must not get secrets (THREAT_MODEL T-01, T-09)

## Considered Options

* A. GitHub Action in the user's repo, user's key in their Actions secrets
* B. Blame-hosted worker (InsForge custom compute) with envelope-encrypted user keys
* C. Local only (`blame review` on the developer's machine)

## Decision Outcome

Chosen option: "A as the default, with C as a second entry point sharing the same code", because A runs on every PR without anyone's laptop being on, costs David nothing, keeps keys and code in the user's GitHub, and needs no always-on server. C gives pre-push reviews and lets "Fix with agent" re-run a check locally. B is deferred until a paying team asks for it (PRD cut C4 logic applies).

How A works:

1. The user adds `.github/workflows/blame-review.yml` (generated by `blame init review`) on `pull_request` (`opened`, `synchronize`, `reopened`). Permissions: `contents: read`, `pull-requests: write`, `id-token: write`. Never `pull_request_target`.
2. The Action restores the code index from `actions/cache`, updates changed files, exchanges its OIDC token at `POST /v1/auth/actions-oidc` for a 10-minute repo-scoped token, and fetches lessons and past bugs.
3. It reviews with the user's chosen provider key (an Actions secret), posts review comments with `GITHUB_TOKEN`, and uploads findings to `POST /v1/reviews/{id}/findings`.
4. Without a Blame account, the Action still works: it reads the brain from the repo's exported `.blame/brain/` markdown if present and skips the upload.

### Consequences

* Good, because zero hosting cost and zero key custody.
* Good, because the runner is a fresh VM per job ([GitHub docs](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners)) and the reviewer never executes repo code.
* Bad, because it spends the user's Actions allowance: GitHub Free includes $12 a month of compute, about 2,000 minutes on a standard Linux runner, and public repos are free ([billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).
* Bad, because on PRs from forks GitHub withholds secrets, so fork PRs are skipped with a visible note. Agent PRs from Cursor and Claude Code are normally same-repo branches, which is the MVP target.
* Bad, because comments appear as `github-actions[bot]` unless the user installs the Blame App for a branded identity later.
* Bad, because setup needs a workflow file and a secret; `blame init review` and the website must make that a two-minute step.

### Confirmation

PRD F24 acceptance: a PR from a non-Blame agent in a connected repo gets a review within 5 minutes p90 over 20 PRs on the test repo; a cache-hit run and a cold run are both timed. Revisit when a design partner refuses to put a key in Actions secrets, when runner minutes become the top complaint, or when the first paying team wants org-wide review without per-repo workflow files.

## Pros and Cons of the Options

### B. Hosted worker
Steelman: one-click install through the GitHub App, branded comments, no workflow file, best UX; what Greptile-style products do.
* Bad, because it needs an always-on worker (beyond 120 h a month on Free), key custody (R-SEC-3 work), and customer code on our servers.

### C. Local only
Steelman: zero cost, zero custody, instant feedback for the author.
* Bad, because it misses PRs when no Blame user's machine is on, and cannot review other agents' PRs reliably (fails DEC-6).
